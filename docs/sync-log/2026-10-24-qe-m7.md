# M7「仿真评测」收尾记录（2026-10-24）

M7 为平台补上第 9 种评测类型 simulation（仿真评测）：用裁判模型驱动的
「用户模拟器」扮演真实用户，与被测 Agent 在每 trial 重置的沙箱环境里多轮
对话，途中注入可恢复的故障逆境，最终以 M2 终态校验器判定目标是否达成，
按 pass^k 口径出指标。落地五个工作项：QE7-1 用户模拟器（persona 引擎/
下一轮消息生成/终止条件）、QE7-2 场景配置校验与回合控制器（环境重置/
回合循环/软超时/停止信号/终态校验/pass^k 聚合）、QE7-3 故障注入（五类
故障、harness 调用层确定性拦截）、QE7-4 仿真 API 与两表（场景 CRUD/
运行生命周期/配额与互斥/停止/进度）、QE7-5 前端（场景构建器/运行列表/
逐 trial 对话回放）。本文件为 M7 验收要求的里程碑收尾 sync-log。

## 一、改动内容

### 用户模拟器（QE7-1）

- `app/services/user_simulator.py`（573 行）：仿真评测的用户侧引擎——
  persona 配置（name/role/goal/expertise（novice|intermediate|expert 或
  0-1 数值）/patience/adversarial/style_hint）与三种组合模式（single /
  blend 多身份合成单用户 / rotate 多用户轮换、已达成 persona 退出轮换）；
  由裁判模型驱动生成下一轮用户消息，应答为 JSON（goal_status/goal_apply/
  progress/action，解析复用 extract_json_from_response，解析失败按确定性
  兜底处理）；终止条件 `check_termination`（优先级 goal_achieved（全部
  persona 目标实质达成）> give_up（模拟器主动放弃或耐心耗尽的确定性失控
  保护）> max_turns）；`record_agent_reply` 记录回合状态并消费 progress/
  action（无进展连续计数，见 QE7-4 遗留 4）。
- LiteLLM 接入约定补落盘（超出 QE7-1 字面范围的配套改动，见遗留事项）：
  `.env.example` 新增「大模型接入约定」节（LITELLM_BASE_URL /
  LITELLM_API_KEY，仅注释行）与 `docs/user_guide.md`「模型配置」节同步
  段——平台一切 LLM 调用统一经 LiteLLM 网关出网，未配置时开发/测试一律
  mock、不调真实付费端点。
- `tests/unit/test_user_simulator.py`（27 个测试）。

### 场景校验与回合控制器（QE7-2）

- `app/services/simulation/scenario.py`（233 行）：场景 config 形态契约
  与归一化纯函数 `validate_scenario_config`——agent（exec_type 白名单
  claude_agent/deepseek_agent 复用既有 harness 拉起与镜像变体 + 自然语言
  指令 + 单次调用超时）、personas/combo_mode（QE7-1 schema）、env（每
  trial staged 的初始文件，相对路径白名单）、verifiers（M2 终态校验器
  配置，**强制至少一个**——无终态校验的仿真不允许发布）、faults（QE7-3
  类型白名单 + 命中回合 turns 归一化，缺省第 2 回合）、trials（1..5 对齐
  pass^k 口径）/max_turns（缺省 15）/trial_soft_timeout_seconds（缺省
  1800s、上限 7200s 对齐 celery task_time_limit）。非法配置抛
  ValueError（发布端点转 400），合法返回归一化 dict。
- `app/services/simulation/turn_controller.py`（422 行）：仿真评测的
  worker 内循环——(1) 环境重置：每 trial 重建工作区
  （`uploads/script_runs/{run_id}/trial-{n}/`，残留 rmtree 后经
  build_run_dir 重建并 staged 场景 env.files），被测 agent 每轮经既有
  execute_harness_in_container 在全新容器（docker run --rm）拉起，工作区
  trial 内跨轮持久、trial 间隔离；(2) 回合循环：模拟器发话 → agent 响应
  （经 harness 沙箱，stdin 携带 user_message 与对话历史）→ 状态更新 →
  终止条件评估；(3) 保护：回合间软超时检查（不打断进行中回合）与停止
  信号（注入式 is_set 协议，RedisStopSignalChecker 兼容）、agent 基础
  设施失败短路 trial（reason=agent_error 不烧完回合）、QE7-3 故障在
  agent 通道边界拦截；(4) 终态校验：对最终工作区与对话跑 M2 校验器
  （file_assert 以 trial 工作区为根，agent 产物 `sim-agent/` 前缀）。
  trial「通过」口径：终态校验 pass 且终止原因非 stopped/agent_error/
  simulator_error（半途中止不计成功；soft_timeout 时终态已可校验、断言
  通过即通过）。多 trial 串行，经 pass_k.trial_pass_stats 出 pass@1 /
  pass^k 并聚合平均回合数。
- `app/services/simulation/__init__.py`（76 行）：域包导出面。
- `tests/unit/test_simulation_controller.py`（25 个测试）。

### 故障注入（QE7-3）

- `app/services/simulation/fault_injection.py`（171 行）：五类可选故障
  策略，全部在回合控制器的 agent 通道边界（`wrap_with_faults` 包装
  AgentCall）**确定性**拦截——命中回合由 config.turns 显式声明，不引入
  随机源（对齐「固定 seed 可复现」纪律）。请求侧：contradiction 矛盾
  指令（用户消息后附加与先前要求矛盾的补充指令）、context_overflow
  上下文超长（消息尾部填充 pad_chars 字符，缺省 10 万、上限 200 万）；
  响应侧：tool_timeout / tool_error（回复替换为故障表态）、dirty_data
  （回复注入确定性乱码/截断污染块）。设计口径（模块 docstring 明确）：
  响应侧故障为「响应边界模拟」——底层 harness 真实执行、命中回合返回
  内容改写为故障形态、会话继续，恢复与否由终态校验判定（故障恢复率 =
  注入命中 trial 中通过的占比）；真实基础设施失败（status != ok）不做
  故障改写。见遗留事项 QE7-3。
- `tests/unit/test_fault_injection.py`（15 个测试）。

## 四、遗留事项（评审逐条核对确认，来源：主线交接材料）

### QE7-1

1. 两处超出 QE7-1 字面范围的配套改动：(1) LiteLLM 接入约定（仓库纪律
   要求同步 .env.example 与 user_guide）此前从未落盘，本次随新增 LLM
   消费方一并补注释（.env.example 仅注释行，不影响 compose env_file
   解析）；(2) 未提前实现属 QE7-2/QE7-3 的回合控制器、故障注入、
   simulation_scenarios 表与 API——它们依赖本模块接口，留待后续工作项
   （注：QE7-2 ~ QE7-4 已在本里程碑内各自落地，见上文改动内容；此处
   按交接原文保留 QE7-1 时点的表述）。

### QE7-2

1. 停止信号为注入式（is_set 协议，RedisStopSignalChecker 兼容）：
   celery 任务接线属后续 API/worker 项，本项控制器不直接依赖 Redis
   （单测无需 Redis）。
2. 「沙箱容器重建」实现为：每轮 agent 调用经既有
   execute_harness_in_container 的 docker run --rm 全新容器 + 每 trial
   工作区 rmtree 重建（未新写容器编排代码——复用即方案要求）。
3. 故障注入 faults 仅做类型白名单校验（QE7-3 接线执行）。
4. QE7-1 的 user_simulator.record_agent_reply 小幅扩展 meta 参数
   （回合执行元信息）。

### QE7-3

1. 工具超时/错误响应/污染数据实现为「响应边界模拟」（底层 harness
   真实执行、命中回合返回内容改写为故障表态）而非真基础设施超时——
   真超时会被 QE7-2 的 agent_error 短路逻辑拦截、会话立即终止，无法
   考察「注入后仍达成目标」的恢复能力；此设计口径已在模块 docstring
   明确。
2. 顺手把方案 §M7 7.1 列出的第 5 类故障 context_overflow 一并实现
   （QE7-2 白名单本就预留了该类型，消息尾部确定性填充 pad_chars
   字符），ask 只点名四类。
3. QE7-2 落盘的单测 test_faults_whitelist_and_passthrough 因 config
   归一化补 turns 键而同步更新断言。

### QE7-4

1. 白名单语义：simulation 入 evaluation_type 白名单但直建该类型评测
   任务被显式拒绝（指向仿真入口）——simulation 的运行单元是场景而非
   任务，evaluation_tasks 不落 simulation 行；方案只说「进白名单与
   统计口径」，此口径已写入代码注释。
2. 结果并入 evaluation_results 体系未做：方案 7.2 原文「新增第 9 种
   类型 simulation，进白名单与统计口径」与「结果并入
   evaluation_results 体系」存在张力，本项把结果落在
   simulation_runs.result（快照冻结、含全部指标），evaluation_results
   体系并入留待评审定夺（属口径决策，不擅自双写）。
3. WS 进度复用 task_status:{run_id} Redis 频道（与评测任务/hub 导入
   同 PubSub→WS 通道，task_status WS 端点对任意 id 订阅即生效），
   未为 run 另开 WS 端点。
4. user_simulator 用户回合明细补 progress/action 两键（工具浪费率
   判定输入）。其余按方案落地。

### QE7-5

1. 文档（README 能力表/user_guide 仿真节）未随本项更新——方案把
   「文档总刷新」排在 M8（届时才允许恢复「9 种类型」表述），避免提前
   夸大口径。
2. 运行进度条采用拉取式（详情/刷新按钮 + completed run 补拉 pass
   口径），WS 实时进度通道后端已就绪（task_status:{run_id}），前端
   实时订阅接入留待后续统一推送面。
