## 四、遗留事项（评审逐条核对确认，来源：主线交接材料）

### QE1-1

1. 节流在方案指定的 (IP+prefix) 5 次/10 分钟→锁 15 分钟精确层之外，加了一层
   IP 全局 30 次/10 分钟→锁 15 分钟（apikey_throttle.py 文档已说明）：盲扫每次
   换随机前缀使 prefix 计数恒为 1，无 IP 层则爆破安全测试无法锁住；方案数值
   未改动。
2. test_webhook_ssrf.py 测的是本项先行的共享守卫原语
   app/services/webhook_url_guard.py——webhook 投递代码属 QE1-3，届时须在每次
   投递前调用 validate_webhook_url（防注册后 DNS 重绑定）；八进制地址变体因
   平台解析行为不一未入真实解析断言集（解析后校验天然覆盖）。
3. README/docs/user_guide 更新顺延至 QE1-4：本项未新增用户可见管理面（无端点、
   无前端改动），仅 .env.example 新增 WEBHOOK_ALLOW_PRIVATE_TARGETS 注释与
   config 默认值。
4. 「API Key 仅放行白名单 scope 化端点」以 scopes.py 内路由注册表在中间件
   集中执法（当前注册表为空=default-deny，API Key 全量 403）；QE1-4 端点落地
   时注册路由并叠加 require_scope 依赖做纵深防御与 OpenAPI 文档化。

### QE1-2

1. 失败/停止收尾的 error verdict 实现在 fail_record/stop_record 内部
   （_attach_gate_error_verdict），而非在每个收尾调用点单独接线——软超时、
   celery on_failure、revoke/用户停止全部路径自动覆盖，且已有判定不覆盖；
   语义与方案一致（落地方式更收敛）。
2. 不可用 metric（含 M2 verification_pass_rate 在 M2 接线前、维度不存在、
   空聚合）判 error 而非 failed：方案未明此分支，取「配置/覆盖问题与质量
   不达标分开」口径（CLI 退出码 2 vs 1），test_gate_semantics.py 有断言。
3. run_task_with_gate 复用既有 POST /run 端点（无新后端旗标）——门禁语义由
   task.gate_config 激活，工具在描述契约上区分（触发后轮询 get_gate_status），
   与 task_run 同 requires_approval=False，符合方案「沿用 Bearer 透传与人工
   审批策略」。
4. tests/security 两文件的注册表 fixture 由清空改为快照/恢复：
   evaluation_task_api 现在 import 期注册路由，清空会抹掉应用注册污染后续用例
   （测试基建修正，非行为变更）。
5. 三个 hub plugin 测试文件的版本断言 1.3.0→1.4.0（版本钉住随契约升级更新，
   manifest 注释规则要求升号）。
6. README/user_guide 更新顺延至 QE1-4/5/6（用户可见管理面与 CLI 落地时统一
   补）；hub 工具的 agent 面文档已在 manifest 描述内更新。

### QE1-3

1. worker-maint 的 stop_grace_period 取 300s（非 eval/ingest 的 7200s 统一
   口径）：maint 任务是秒级 HTTP 投递，无长任务退出窗口需求；
   test_celery_queue_split.py 增加按服务分档的 WORKER_STOP_GRACE 映射并新增
   worker-maint 绑定断言（契约钉住随新服务更新）。
2. 事件发射收口在 TaskExecutionRecordService.complete_record/fail_record 单一
   查点（覆盖软超时/on_failure/OperationalError 重试等全部 complete/fail
   路径）；stop_record 不发射（方案事件清单仅 completed/failed/gate.failed）。
   gate.failed 仅在 verdict=failed 且完成时发，报文携带完整 gate_result。
3. webhook secret 库内存明文（与 API Key 只存哈希不同）：HMAC 签名需原值参与
   运算，模型注释已说明；仍仅创建时返回一次。
4. 重试语义：celery self.retry countdown 30/60/120s、max_retries=3（总尝试
   4 次）。
5. docker-compose.dev.yml/docker-compose.scale.yml 未动：仓库无 dev compose
   worker 定义（grep 无 CELERY_WORKER_QUEUES 命中），scale 拓扑由
   test_compose_scale_topology 继续覆盖原口径。
6. README/user_guide 更新仍顺延至 QE1-6 前端管理面落地时统一补。

### QE1-4

1. results:read 只覆盖四个 GET 端点（含 dimension-trend）；POST
   /history/{n}/export 是写操作（生成+上传文档），按方案表（仅 GET
   /evaluation/results/...）保持登录态专用，测试钉住 API Key 不可达。
2. api-keys 列表/吊销口径为「本人创建的 Key」（超管可代吊销，但列表仍只看
   本人）——Key 是个人凭证，不按团队共享；他人 Key 按归一 404 口径防存在性
   探测。DELETE 实现为吊销（revoked_at 软删幂等，审计留痕），非物理删除。
3. 无新迁移（复用 QE1-1 api_keys 表）。
4. README/user_guide 仍顺延至 QE1-6 前端管理面落地时统一补。

### QE1-5

1. 方案端点清单未列 datasets 路由的 scope 授权，但 aievo datasets upload 依赖
   API Key 调用，故按现有 datasets:write 常量补齐了注册与 require_scope（读

2. e2e 桩不走 complete_task 的 stats 收尾路径（stats duration 在 sqlite 下

   无关），改为直接落任务终态+执行记录+门禁判定，等价 worker 稳态。
3. typer/httpx 依赖由 requirements.lock 既有序列满足，未改 requirements.txt/
   lock（CLI 自身依赖在 cli/pyproject.toml 声明，wheel 可独立构建）。
4. GitHub Action 模板为 composite action 形态落盘为
   ci-templates/github/action.yml，跨仓库引用名 aievo/gate@v1 需发布后生效，
   文档已注明同库/跨库两种引用方式。
5. 方案中『GitHub Action 在本仓库 CI 真实自举』与『本地起栈端到端』属 M1
   验收集成项，本项以 uvicorn 真栈 e2e 覆盖 0/1/2 全码，自举 workflow 留待
   验收轮。
